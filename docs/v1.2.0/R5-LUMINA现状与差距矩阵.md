## 0. 一句话结论

**当前架构支撑「LR 全量对标」，不支撑「PS 全量对标」。**
必须先做一次**渲染内核重构**（8bit sRGB 单 pass 近似 → 16bit 线性工作空间 + 单一渲染图 + 预览导出一致），这是最小切口；`图层树 / 选区 / 文字 / 矢量` 所需的「文档模型」是第二次重构，建议明确不做 PS 全量、只做 PS 的 5 个高频能力。

最刺眼的三条事实（后文有证据行）：

1. **预览 ≠ 导出**：`EditParams` 有 **93 个参数叶**，GPU 预览真正参与像素运算的只有 **39 个**，导出链路只有 **27 个**。高光/阴影/色温/曲线/蒙版/裁剪/镜头在导出时**全部丢失**。
2. **图层是摆设**：`lumina:AdjustmentStack` 有完整数据结构 + 面板 + 落盘，但**没有任何渲染器读它**，`removals` 更只有一行 XMP 映射。
3. **8bit 天花板**：解码写死 `output_bps = 8 / output_color = sRGB`（`raw_decoder.cpp:58-59`），全链路 `uint8_t[3]`，无线性工作空间、无 ICC——这是"对标 PS"的硬天花板，不是功能缺口。

## 4. 最刺眼发现：参数模型 ≫ 渲染模型

### 4.1 三个数字

| 阶段 | 参与像素运算的参数叶 | 占比 | 证据 |
|---|---|---|---|
| **参数模型**（`EditParams` 定义） | **93**（含 24 HSL + 8 分级 + 7 校准 + 7 细节 + 8 光学 + 13 几何 + 4 曲线 + 7 参数曲线） | 100% | `app/src/api/protocol.ts` EditParams |
| **GPU 预览**（`shaders.ts`） | **39**（12 基础 + 1 复合曲线 + 24 HSL + 2 效果） | **42%** | `renderer.ts:54-69` `paramVector` 只填 12 槽；`shaders.ts:292-330` |
| **导出**（`exporter.cpp`） | **27**（曝光/对比/饱和 3 + 24 HSL） | **29%** | `exporter.cpp:724-742` |

**推论**：用户在当前版本调整"高光/阴影/白平衡/清晰度/曲线/蒙版/裁剪"，**预览看得见，导出全部丢失**。这不是"功能少"，而是**产品诚信风险**——比缺功能严重一个量级。

### 4.2 假控件清单（参数可存可调、像素不动）

| # | 控件 | 预览 | 导出 | 代码位置 | 备注 |
|---|---|---|---|---|---|
| 1 | 纹理 | ✗ | ✗ | `paramVector` 无 texture 槽位 | UI 有滑块（`ProPanel:236`） |
| 2 | 分通道曲线 R/G/B | ✗ | ✗ | `buildCurveLut` 只用 `toneCurveRGB` | 存储正常 |
| 3 | 参数曲线（7 项） | ✗ | ✗ | 全库无消费点 | —— |
| 4 | 颜色分级（8 项） | ✗ | ✗ | shader 无 uniform | 面板完整 |
| 5 | 校准（7 项） | ✗ | ✗ | shader 无 uniform | 面板完整 |
| 6 | 锐化 / 亮度降噪 / 彩色降噪（7 项） | ✗ | ✗ | 无算子 | 面板完整 |
| 7 | 镜头配置文件 / 手动畸变 | ✗ | ✗ | 无 lensfun | —— |
| 8 | 裁剪 / 拉直 / 透视（13 项） | ✗ | ✗ | 无几何变换阶段 | `TransformBar` 全组失效 |

| 12 | 调整图层栈 / 修复笔画 | ✗ | ✗ | 无渲染器消费 | 仅落盘 |

> 建议：QA 在 v1.2.0 立项前对 1–12 逐条出「控件可见性」结论。专业面板的 30+ 滑块中，**有一半以上当前不产生任何像素变化**——这是"专业模式"承诺与实际能力之间最直接的落差。

### 4.3 为什么会出现这种落差（根因，非态度问题）

1. **两套管线、两套算子、两个作者**：预览在 TS 侧（`shaders.ts`），导出在 C++ 侧（`exporter.cpp`），参数语义靠"同源注释"口头保证，**没有逐像素一致性测试**（HSL 是唯一做了 `meanAbsDiff=0` 断言的参数）。
2. **UI 先行、渲染后置**：v1.0.0 的验收口径是"界面与交互全部实现 + 业务逻辑真实可跑"，参数持久化（XMP round-trip）被当作"功能达成"，渲染深度未被卡口。
3. **没有渲染图（RenderGraph）抽象**：任何新参数都要同时改 shader、CPU 软渲染、导出三处，成本高 → 自然被推迟 → 沉淀为假控件。

## 5. 架构层面的根本差距（比功能清单更重要）

### 5.1 数据模型：RAW 中心 + 目录库 vs 文档中心 + 图层树

| 维度 | LUMINA | PS | LR |
|---|---|---|---|
| 一等公民 | **照片条目**（1 行 DB + 1 个 sidecar） | **文档**（画布 + 像素 + 图层树） | 照片条目（1 行 DB + 私有 settings 串） |
| 非破坏载体 | `EditParams` 扁平 93 叶 | 图层/智能对象/调整图层 | develop settings 串 |
| 多结果 | 虚拟副本（共享源 + 独立参数） | 画布内多图层 | 虚拟副本 |
| 派生关系 | **无** | 智能对象引用 | 无（合成产物独立成片） |
| 存储 | XMP sidecar（开放、可移植） | .psd/.psb（私有二进制） | .lrcat（私有，已损坏过一次） |

**要不要引入图层树？——要，但不是 PS 的那种。**

- **PS 式图层树 = 像素栈**：每层是独立像素缓冲。引入它必然要求"文档容器"（.psd 或 .lumina 工程文件），**与 R1「参数即文件、sidecar 可被任何工具读取」正面冲突**：sidecar 存不了 500MB 像素。
- **建议引入的是「参数节点链」（NodeGraph）**，把现有 `AdjustmentStack` 从 JSON 摆设升级为**可执行的有序节点序列**：
  - 节点类型先只做 4 种：`调整节点`（现有参数组）/ `局部节点`（蒙版）/ `修复节点`（笔画 + 像素补丁入缓存）/ `源节点`（引用 RAW 或合成产物 + 版本指纹）。
  - 存储仍走 sidecar：`lumina:NodeGraph`（SchemaVersion 1 → 2）；同时把节点链"投影"回 `crs:` 扁平字段，**保证 LR/Acrobat 侧仍能读到基础调整**（双向兼容，这是我们的独有资产）。
  -  coexist 成本：中（一次字段迁移 + 一个 CPU 参考实现），收益：一次性解决"图层假控件 + 派生关系缺失 + PSD 图层导出无内容"三个问题。

> 结论：**不做像素图层，做参数节点**。真正需要像素图层时（选区填色、文字描边、矢量形状），只在**导出/工程文件**层面存在，不进目录库。

### 5.2 非破坏性语义：参数 vs 智能对象 + 智能滤镜栈

| 语义 | PS 智能对象 | LUMINA 现状 | 后果 |
|---|---|---|---|
| 引用 | 引用外部文件，双击可改源 | 无引用，合成产物是**新照片条目** | 改了源 RAW，HDR 产物不变；用户以为联动 |
| 参数化滤镜 | 智能滤镜栈（可回改顺序） | HDR/降噪是**一次性 job**，结果入缓存 | 参数改一个值要重跑整条 job |
| 嵌套 | 智能对象套智能对象 | 无 | 无法"先降噪再合成再局部" |
| 可回退 | 随时删除滤镜 | 只能删产物重建 | 成本高，用户放弃精修 |

**判据**：`lumina:CompositeSourceRefs`（v1.2 PRD §7 已规划）只解决"记录来源"，**不解决"可重算"**。要"可重算"，必须有节点图 + 缓存键（源指纹 + 参数指纹）。这是 5.1 的同一块钱。

### 5.3 渲染管线：顺序在哪一层、缺哪几步

**现状：两条互不相干的管线，没有共享中间表示。**

```
预览（TS/GPU，单 pass，sRGB 域）：
  tex(sRGB8) → srgb2lin → 曝光 → HSL 权重(高光/阴影/白/黑) → 对比 → 色温/色调
  → 去雾/清晰 → 曲线LUT → HSL8带 → 蒙版×6 → 暗角 → 颗粒 → out

导出（C++/CPU，8bit，sRGB 域）：
  LibRaw(AHD, 8bit, sRGB, camera WB) → 缩放 → 曝光/对比/饱和 → HSL8带
  → 色彩空间矩阵 → 水印 → JPEG/TIFF/PNG
```

**与 LR 管线顺序对比，缺 7 步：**

| # | LR 阶段 | LUMINA | 影响 |
|---|---|---|---|
| 1 | 线性 ProPhoto 工作空间（16bit） | 无（8bit sRGB） | 高光/阴影迭代后色阶断裂，HSL 双重量化 |
| 2 | 相机配置文件（DCP/LookTable） | 无 | 色彩"不像原厂"，无法按机身校准 |
| 3 | 白平衡（线性域，色温真实 K 值） | 近似（`(temp-5500)/25` 线性偏移） | 色温滑块与 K 数不对应，跨图不一致 |
| 4 | 局部调整（蒙版在**管线中段**） | 预览有、导出无 | 见 §4.1 |
| 5 | 细节阶段（亮度/色彩降噪 → 锐化 + 掩蔽） | 无 | 无输出锐化，缩图后发软 |
| 6 | 镜头校正（畸变/暗角/色差，在变换前） | 无 | 建筑/风光直线不直 |
| 7 | 几何（透视/裁剪）→ 输出色彩空间 → 输出锐化 | 无 | 裁剪完全无效（最容易被用户发现） |

**结论**：不是"少几个滤镜"，而是**管线本身不成立**——它只有"色调近似"一段。要补，必须在引擎里建**唯一的渲染图（CPU 参考实现）**，然后 GPU 预览 = 该图的 GPU 后端、导出 = 该图的 CPU 后端，CI 做逐像素比对（ΔE00 ≤ 1）。这是最小切口的**技术核心**。

### 5.4 依赖硬约束（哪些是 v1.2.0 绕不过去的）

| 依赖 | 是否硬约束 | 说明与处置建议 |
|---|---|---|
| **LibRaw 0.21.4（静态）** | **硬** | ① 新机型压缩格式只能跟随上游（S5M2 已覆盖，2026 年新机风险）；② LGPL 静态链接需提供可重链接目标文件（合规动作，非阻塞）；③ 单线程编译（`LIBRAW_NOTHREADS`）→ 全尺寸导出 4.6s/张，批量导出吞吐受限。**建议**：升级到 0.22.x 分支 + 打开线程，作为 v1.2.0 M0 动作（约 3 人日，风险低）。 |
| **8bit 管线（自研）** | **最硬** | `imaging::Image` 是 `uint8_t[3]`，被 30+ 处引用。改 16bit 线性是**全链路手术**（解码/缩放/算子/编码/水印/缩略图），20 人日是最低估。**这是"能否对标 PS"的唯一开关**。 |

| ffmpeg（外部） | 软 | 延时可用性依赖用户环境。建议随包内置（分发体积 +80MB），否则"延时全链路内置"是空话。 |

## 8. 结论与最小切口

### 8.1 判断

> **现有架构支撑「LR 全量对标」，不支撑「PS 全量对标」；要做 PS 类能力，必须先做一次渲染内核重构，且这次重构不需要推翻目录库、XMP、IPC——这是好消息。**

理由（三条，按重要性）：

1. **目录库 / XMP / 103 方法 IPC 是资产，不是包袱**。它们解决了 PS 与 LR 都没解决的事（不锁库、可移植、缺失透明）。任何重构都不应触碰这一层。
2. **真正需要重写的是"像素层"**：`imaging/`（320 行）+ UI shader（331 行）+ `exporter.cpp` 内联算子。这一层薄、散、无抽象——**重写成本低、收益高**，是理想的重构靶点。
3. **PS 的图层/选区/文字/矢量需要"文档模型"**，那是第二套数据通路（工程文件），与 sidecar 模型并列。**是否引入是产品决策，不是技术决策**——建议明确"不做"，只做 PSD 单向写（把参数节点投影成图层），保留"回到 PS 继续精修"的出口。

### 8.2 最小切口（3 步，按顺序，不可并行）

| 步 | 动作 | 产出 | 人日 | 验收 |
|---|---|---|---|---|

**S1 是关键**：它一次性解决三个根本问题（预览≠导出 / 8bit 天花板 / 缺细节与几何阶段），且**改动面收敛在 320 行的 `imaging/` + 331 行 shader + 80 行导出算子**，不动 DB/XMP/RPC。做完 S1，再走 B 路线（LR 对标）的边际成本会显著下降。

### 8.3 给 v1.2.0 立项的三条硬建议

1. **把「M0 止血」写进任何版本**：预览≠导出是**当前在线版本**的缺陷（不是 v1.2 的功能），应作为 v1.1.2 或 v1.2.0 的第一个里程碑，不与新功能混排。
2. **重写范围口径**：v1.2.0 从「八项功能」改为「**渲染内核 + 色彩与打印 + PSD 出口**」三件套；全景/景深/星空/移动端全部下沉到 v1.3。
3. **设一条新红线 R7「所见即所得」**：任何参数在 UI 可见，必须同时满足「预览生效 / 导出生效 / 有像素断言」三条，否则不得上线。这条红线比现有 R1–R6 更能阻止能力虚胖。
