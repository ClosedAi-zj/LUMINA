## 0. 一页决策摘要

**v1.2.0 的性质由「补八项功能」改为「渲染内核重建」。**

三条支撑事实：

1. **导出链路只应用 27/93 个参数叶（29%）**，预览应用 39 个（42%）。导出实际只读 `exposure / contrast / saturation / hsl` 四项（`engine/src/export/exporter.cpp:719-742`），高光、阴影、白、黑、白平衡、曲线、清晰度、去雾、蒙版、裁剪、镜头校正**全部丢失**。这是**在线正确性缺陷**，且完全静默，直接违反红线 R3。
2. **存在三套互不相等、无对拍测试的渲染实现**：WebGL 预览（`app/src/modules/develop/webgl/`）、Canvas CPU 回退（`cpu-render.ts`）、引擎导出（`exporter.cpp`）。三者不共享参数结构，"口径靠人记"。
3. **8-bit sRGB 天花板**：`raw_decoder.cpp:58-59` 写死 `output_bps=8 / output_color=sRGB`，`imaging::Image` 为 `uint8_t[3]`，全链路无线性工作空间、无 ICC。这决定"对标 PS"在数学上不成立。

**结论**：先修裁判，再谈功能。v1.2.0 = M0 地基 → M1 求值器统一 → M2 LR 闭环 → M3 PS 出口 → M4 色彩与打印。

**规模**：LR 全量对标 **204 人日**（含 M0 止血 35 人日）；加 PSD 写 + 修复画笔 + 变换 + 文字 **265 人日**；PS 全量精修 305 人日、生态 175 人日（不在本版）。2 人并行约 4 个月。

## 1. 现状体检：三个结构性缺陷

### 1.1 缺陷 A：预览 ≠ 导出（P0，在线正确性）

| 环节 | 参数叶生效数 | 证据 |
|---|---:|---|
| GPU 预览（WebGL） | 39 / 93（42%） | `app/src/modules/develop/webgl/renderer.ts:54-69` + `shaders.ts` |
| Canvas CPU 回退 | 与预览同口径（自述） | `app/src/modules/develop/cpu-render.ts` |
| 引擎导出 | 27 / 93（29%） | `engine/src/export/exporter.cpp:719-742` |

导出侧代码只做三件事：取 `exposure/contrast/saturation` → `applyToneApprox` → HSL 8 色带 `applyHslApprox`，然后直接进色彩空间转换、水印、缩放。**没有任何一处读取高光/阴影/白平衡/曲线/清晰度/蒙版/裁剪/镜头参数。**

危害：用户调图后导出得到的是一张"只有基础四项"的图，且无任何提示。摄影师场景下这等于交付废片。

### 1.2 缺陷 B：假控件（参数能存、UI 能调、像素不动）

R5 盘点出 12 类假控件：纹理、分通道曲线、参数曲线、颜色分级 8 项、校准 7 项、锐化/NR 7 项、镜头配置、裁剪/透视 13 项、暗角中点、颗粒大小、**范围蒙版（可切换但回落画笔分支静默失效）**、调整图层栈。

专业面板 30+ 滑块里过半当前不产生任何像素变化。这比"缺功能"更坏：它让用户以为自己在精修。

### 1.3 缺陷 C：数据模型三处硬伤（卡住 v1.2.0 部分验收）

| 硬伤 | 现状 | LR 的做法 |
|---|---|---|
| 照片身份 | `photos.file_path` 全路径 UNIQUE —— 把路径当身份 | 四级表：图像 ↔ 文件 ↔ 文件夹 ↔ 根 |
| 调整参数 | 只在 XMP sidecar，库内仅 `has_edits` 布尔 | 库内 develop_settings 表，可按调整筛选、可原子备份 |
| 历史记录 | **只在内存**（`engine/src/edit/history.h`，无表无 DAO），重启即丢 | 实测存 52,913 步 |

### 1.4 结构能力盘点

✅ 6 / 🟡 17 / ⬜ 21（详见 R5）。

- **强项全部在数据可靠性**：sidecar 可移植、缺失透明、MD5 全链路、离线地图、延时内置 —— 这几项对 LR 是**真实反超**，v1.2.0 不得回退。
- **弱项全部在像素运算**：线性工作空间、色彩管理、几何阶段、局部蒙版的数学正确性、锐化/NR。

## 2. PS / LR 逆向结论（机制级）

### 2.1 Photoshop：唯一值得整体照搬的是「智能滤镜节点栈」

智能滤镜不是"滤镜列表"，而是 `{filterId, params, mask, blendMode, opacity, enabled}` 的**可重入节点栈**，带三条硬前提：

1. 滤镜必须确定性（同参数同输入 → 同输出）；
2. 缓存键必须完整（漏一个参数就是脏缓存）；
3. 外部依赖（字体/模型/文件）缺失时**跳过并保留缓存**，而不是崩溃或静默换结果。

再加一条乐观并发规则：文档/版本/图层/滤镜四元组变了，必须重开对话框。

**对 LUMINA 的意义**：把 `camera-raw` 做成栈底节点，RAW 参数与图层滤镜就共用一套求值器。这是「RAW 中心」与「图层中心」唯一不别扭的合流方式，也正是 NodeGraph 的形态依据。

其余关键结论：

- **PSD 内嵌 merged composite = 免费的官方考题**。用自家合成器渲染图层与该合并图逐像素比对，等于零成本获得一套官方一致性测试集（对标项目用地板值 190/258）。**本迭代即可执行**。
- **XMP 必须是唯一真相源，PSD 只做单向派生**。PS 是图层树、我们（改造后）是参数节点图，范围蒙版在 PS 无对应物，双写必产生双真相源。做法：PSD 内写两份（图层结构 + 每层 `layer.xmpMetadata` 中的 `lumina:` 快照）；无快照时降级为像素层并**显式告知**，绝不静默合并。
- 工作量分档：必须抄 10 项 ≈ **130–200 人日**；可晚抄 10 项；坚决不抄 8 项（3D 60–120、视频 40–80、印刷前端 50–100、`.8BF`/UXP 宿主 60–120 + 法务）。

### 2.2 Lightroom：管线顺序是产品本身

**20 个阶段里我们只有 3 个真正对齐**（曲线 LUT、HSL 结构、暗角/颗粒）。三处结构性错位：

1. **白平衡排在对比之后**（`shaders.ts:129-135`）——LR 中它是第一位，必须在任何色调运算之前作用于线性原始数据；
2. **全程 8-bit sRGB 域**（`shaders.ts:64-65,110`）——曝光/高光在 gamma 空间数学上就不对；
3. **光学/几何/细节整段缺失**——镜头校正、变换、裁剪、锐化、降噪全无阶段。

修正代价 18–30 人日，**且越晚做，sidecar 里已有的历史参数越难迁移**（因为参数语义会变）。

其余关键结论：

- **非破坏性四件套**：history（落盘）/ snapshots / virtual copies / presets+profiles，语义各不相同，不能用一个"版本号"混过去。
- **色彩科学追不平**：连投入 20 万行 Rust + 2,500 测试的对标实现，对相机 JPEG 的 ΔE 中位数也只有 5.0–5.1，且从未测过对 Adobe Standard 的差距。这条必须在开工前决策（见 §6）。
- **互操作是单向的**：我们目前只写 `lumina:Masks`/`lumina:Removals`，LR 读不到。要双向必须双写 `crs:MaskGroupBasedCorrections` + `crs:RetouchAreas`。
- **合成产物形态**：F1 全景/F2 堆栈若输出 JPEG/TIFF，就等于放弃"产物可继续非破坏性编辑"。应输出 16-bit 线性 DNG，并配 `lumina:CompositeSourceRefs`。

### 2.3 两个开源项目的可借鉴 / 不可借鉴

| 维度 | 可借鉴（架构思想） | 不可借鉴（或需自研） |
|---|---|---|
| 渲染 | 单一 `Plan` 驱动 CPU/GPU；CPU 为 oracle、GPU 为优化；等价判据 mean\|Δ\|<0.5、max≤3 LSB（实测 1 LSB）；三键阶段缓存 | 其 RAW 解码实现（血统与许可） |
| 管线 | 五段式 geometry → scene-linear → tone map → colour → display；13 步严格有序；**resize 属几何阶段** | 其 Color Science 数值 |
| 工程 | 「规则 = 检查」：clippy deny 全覆盖、xtask 强制分层、parity 表驱动 + 地板值断言、scorecard 防手改 | — |
| 撤销 | COW tile 快照的正确性收益（后台作业/自动保存/无锁读免费） | **全文档 clone 的性能代价**：改不透明度 276ms（目标 20）、切可见性 178ms（目标 10）、复制 12MP 图层 508ms（目标 100） |
| 目录库 | 派生索引惰性+增量、导入只读文件头、100k 规模基准进 CI | 它的 JSON Lines op log（我们已有 SQLite，迁移不划算） |
| 风险 | — | 多套渲染实现靠人工对齐（= 我们当前的缺陷 B）；8-bit 域叠加调整；单次 submit 无限切分导致 GPU device lost；字体同步扫描导致 UI 冻结 60s；Content-Aware Scale 954s |

**必须立刻定的一件事**：顺序可以后补，"谁是裁判"必须现在定。R4 的原话——否则 v1.2 每加一个功能都在扩大三套实现之间的裂缝。

### 5.2 硬验收口径（新增红线）

**R7 所见即所得**：任何 UI 可见参数，必须同时满足「预览生效 / 导出生效 / 有像素断言」。三格缺一格，不算完成，不许上线。

配套三条机器判据：

1. 参数叶覆盖率 = 93/93，逐叶记录在 CI 产物里；
2. CPU vs GPU 等价：mean\|Δ\| < 0.5、max ≤ 3 LSB；
3. PSD 合成对拍：以 PSD 内嵌 merged composite 为 oracle，设地板值并只许升不许降。

## 6. 三个必须由用户决策的问题（开工前）

### 6.1 NodeGraph 的粒度（已定方向，待定粒度）

前提已定：升级为参数节点链。待定的是**节点粒度**：

- **粗粒度**（一个节点 = 一个模块，如"基础面板""颜色分级"）：迁移简单、投影 `crs:` 容易，但无法表达"单独的曲线在蒙版内"这类组合；
- **细粒度**（一个节点 = 一个参数叶）：最灵活、最贴近智能滤镜，但 `crs:` 投影会变得非常复杂；
- **折中（建议）**：节点 = 「参数组 + 可选蒙版 + 可选混合」，即 8 个左右节点类型，既覆盖 `crs:` 全部字段，又能容纳局部调整。

### 6.2 色彩科学路线（三选一，不可拖）

- **A 自建 5–10 个机型 DCP 等价物**（松下 S5M2 必做，占用户图库 92.2%）：最贴近 LR，但成本最高、需要色卡实测；
- **B 明确宣告"自有色彩科学"**，验收口径改为"对相机 JPEG ΔE ≤ 3"：诚实、可达成，但放弃"像 LR"的叙事；
- **C 只做第三方 `.dcp` 加载器**，不内置、不分发：合规且轻，但用户需自备配置文件。

不决策的后果：「像不像 LR」这个验收口径永远悬空，M2 无法收口。

### 6.3 LibRaw 处置（合规，不是技术）

更正一个此前流传的错误前提：**LibRaw 是 LGPL-2.1 / CDDL-1.0 双许可，不是 GPL**。真实冲突分三层：

| # | 冲突 | 性质 |
|---|---|---|
| 1 | 静态链接 `libraw.a`（`engine/CMakeLists.txt:104`）+ 全静态运行时 | LGPL-2.1 §6：静态分发须提供可重链接材料，或改动态链接 |
| 2 | 血统源自 dcraw（GPL） | **clean-room 主张不成立**（仅 RAW 模块） |
| 3 | 对外表述 | 若既静态链 LibRaw 又宣称引擎 clean-room，声明为假 |

五条路：**A 换自研解码器**（最高代价）→ **D 隔离为独立进程/.dll** → **B 改动态链接** → **C 维持静态 + 补齐 relink 材料** → **E 只改表述**（最低且不合规）。

**建议**：v1.2 走 **C**（合规成本最低），同时**不宣传 clean-room**；并把"RAW 解码方法论四件套"作为 B/A 的前置先建起来——能力矩阵、CC0 语料 + 输出指纹、黑盒 oracle 只取像素、每个不支持变体返回具名 `Unsupported`。这四件套无论走哪条路都要做，且零风险。

## 7. 工程纪律（从两个项目抄过来，可立即落地）

| 规则 | 落成检查 | 迁移成本 |
|---|---|---|
| 参数叶不许是假控件 | CI 解析 93 叶 → 断言每个叶在预览/导出代码路径中出现 | 低 |
| 分层不许穿透 | 脚本解析 `CMakeLists.txt` 的 `target_link_libraries` 强制依赖方向 | 低 |
| 不许 panic / 不许裸异常 | clang-tidy 规则集 + `-Werror` 分级 | 低 |
| parity 不许倒退 | 表驱动清单 + 地板值断言（只许升） | 中 |
| 性能不许退化 | 关键场景基准进 CI，超预算即失败 | 中 |
| 未知数据不许丢 | PSD 未知 tagged block 往返字节一致断言 | 低 |
